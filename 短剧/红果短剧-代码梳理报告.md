## 1. 当前实际生效链路（播放）

```
play()
  → 返回 http://HOST:10008/media.mp4?vid|sid&q=...   （内置 CENC Range 流服务地址）
  → serveMediaHttp() → mediaSession()
      → videoModel() → videoModelOnce()
          → registerPlaybackDevice()  [匿名设备注册]
          → 多集群尝试（steps）：
             ① VIDEO_APIS × 5（multi）→ playbackRequest() → signPlaybackV5() → v5Medusa()【v2.2.5 新版36字段】
             ② SHORTPLAY_APIS × 3（shortplay）→ shortplayRequest() → PlayerSigner.headers() + genMedusa()【旧版v04.06.04】
             ③ 1.5s 后 lq 集群重试
             ④ video_tab GET fallback → signPlaybackV5() → v5Medusa()
      → selectQuality() → mediaUrl()/resolvePlaybackUrl() [v2.2.2]
      → deriveContentKey() [v2.2.3 v1常量250 / v2.2.2 动态切分]
      → fetchMoov() → CencMediaSession() → 206 明文推流
```

## 4. 需要警惕的矛盾点

1. **字段21 三个值之争**：open-apex SDK 说 369（真机）/377（模拟器被拒）；hongguoTV 11-23 文档说 312；hongguoTV 11-25 最新 PR#122 仍用 312 且强调"完整信封才是关键"。当前采用 **312 + 36 字段**（最新且带完整实测）。若失败，优先回到这里。
2. **两套 medusa 并存**：V5 主路径用新 v5Medusa（36字段），shortplay 用旧 genMedusa（v04.06.04）。它们服务不同接口，不是简单重复，但增加了维护成本。
3. **legacy shortplay 路径**：hongguoTV 最新版已完全不用 video_model/v1，脚本仍保留作兜底。其签名（PlayerSigner + 旧 genMedusa）与当前服务端要求可能不匹配，但只在 V5 全部失败时才走到。
4. **@description 流水账**：十几版修复记录全部堆在头注释，建议后续精简为"当前状态 + 最近一版"，历史移本文件。

## 5. 建议（本次未执行，避免大改引入风险）

- **保留死代码**（coreSixgod 及专属依赖）：当前无调用、不影响运行；删除收益小、回滚成本高。
- **不删 shortplay**：虽然过时，但作为最后兜底无害。
- **下一步若仍播放失败**：优先验证 v2.2.5 的 v5Medusa 与真实请求是否完全对齐（可用 hongguoTV 合成向量做确定性对照），再考虑是否需要：
  - 把 `v5Carrier` 用 hongguoTV 的 carrier 向量验证；
  - 统一两套 medusa 到新版信封。
